# 請求書読み取りツール 作業書

## 1. 目的

「業務システムにAIを組み込める」ことを見せるための作品。

見せたい強み：
- AIで読み、プログラムで確かめ、怪しいものは人に回す、という設計判断
- DB設計と業務システムの作法（仮テーブル、二重登録の防止、修正履歴）
- 簿記の知識（税率ごとの計算、内税と外税、源泉所得税、仕訳）
- 精度を数字で測って示すこと

## 2. 全体の流れ

1. `data/inbox/` にPDFか画像が入る
2. `data/processing/` に移す
3. PDFなら文字を直接取り出す。取り出せなければページを画像にする
4. 文字か画像をAIに渡し、決まった形のJSONで項目を受け取る
5. 結果を仮テーブル（staging）に入れる
6. 検算する
7. 通ったら本番テーブルへ登録し、原本を `data/done/` に改名して移す
8. 引っかかったら状態を「要確認」にし、理由を保存して `data/review/` に移す
9. 人が確認画面で直し、検算をやり直して承認する
10. 承認済みのデータから仕訳CSVを出力する

読めないファイルや壊れたファイルは `data/error/` に移す。

## 3. 役割分担

| 担当 | やること |
|---|---|
| AI（Anthropic API） | 請求書から項目を読み取る |
| プログラム | 検算、二重登録の確認、フォルダ移動、DB登録 |
| Jev（任意） | 読み取った値の照合、勘定科目の選択、手書きの判定 |
| 人 | 要確認の修正と承認 |

## 4. 実行時のフォルダ

```
data/
  inbox/        届いたファイル
  processing/   読み取り中
  done/         登録済みの原本（YYYYMMDD_発行元_請求額.pdf に改名）
  review/       検算で引っかかったもの
  error/        壊れたファイルなど
  invoices.db   SQLite
```

`data/` はGitに上げない。フォルダがなければプログラムが作る。

## 5. AIから受け取るJSON

```json
{
  "invoice_no": "INV-2026-7771",
  "issuer": "瀬戸内サンプル物流株式会社",
  "registration_no": "T8999900000001",
  "recipient": "株式会社テスト商会",
  "issue_date": "2026-09-30",
  "due_date": "2026-10-31",
  "tax_mode": "外税",
  "taxable_10": 108680,
  "tax_10": 10868,
  "taxable_8": 0,
  "tax_8": 0,
  "withholding": 0,
  "total": 119548,
  "is_handwritten": false,
  "lines": [
    {"name": "倉庫保管料", "qty": 1, "unit": "月", "price": 39500, "amount": 39500, "rate": 10}
  ]
}
```

決まりごと：
- 金額はすべて整数（円）。カンマや円記号は付けない
- 日付は `YYYY-MM-DD`。和暦（令和8年）は西暦に直す。年が書かれていない日付は発行日の年から補う
- `tax_mode` は「外税」か「内税」
- `taxable_10` と `taxable_8` は常に税抜の額。内税の請求書では、税込額から消費税を引いた額
- `total` は請求書に書かれている請求額をそのまま入れる。AIに計算させない
- 読み取れない項目は `null`。推測で埋めさせない
- 値引きの行は金額をマイナスで入れる

## 6. DB

| テーブル | 主な列 |
|---|---|
| `staging` | id, file_name, file_hash, 5の各項目, status, errors（JSON）, source（text / image）, created_at |
| `invoices` | id, staging_id, 5の各項目, original_path, approved_by, approved_at |
| `invoice_lines` | id, invoice_id（またはstaging_id）, name, qty, unit, price, amount, rate |
| `corrections` | id, staging_id, field, old_value, new_value, corrected_by, corrected_at |

- `status` は `pending` / `passed` / `review` / `approved` / `error`
- `file_hash` はファイルの内容のSHA-256。同じファイルが二度届いたら処理しない
- `invoices` には（発行元, 請求書番号）に一意制約を付ける
- DBへの接続とSQLは `db.py` にまとめ、他のファイルから直接SQLを書かない

## 7. 検算

`validate.py` に、エラーの一覧を返す関数として作る。一覧が空なら通過。

| 確認 | 内容 |
|---|---|
| 必須項目 | 請求書番号、発行元、発行日、請求額が空でない |
| 明細の合計 | 外税：税率ごとの明細の合計が `taxable_10` / `taxable_8` と一致。内税：明細の合計（税込）が `taxable + tax` と一致 |
| 消費税 | 外税：`taxable × 税率` の切り捨てと一致。内税：`税込額 × 税率 ÷ (100 + 税率)` の切り捨てと一致。どちらも1円の差は許す |
| 請求額 | `taxable_10 + tax_10 + taxable_8 + tax_8 − withholding` が `total` と一致 |
| 源泉所得税 | 0でなければ、`taxable_10 × 10.21%` の切り捨てと一致（1円の差は許す） |
| 登録番号の形 | `T` ＋ 数字13桁 |
| 登録番号の検査数字 | 下の計算で1桁目と一致 |
| 日付 | 実在する日付で、支払期日が発行日より後 |
| 二重登録 | 同じ発行元と請求書番号が `invoices` にない |
| 手書き | `is_handwritten` が真なら、他が通っていても要確認にする |

登録番号の検査数字：`T` の後ろの13桁のうち、1桁目が検査数字、残り12桁が本体。本体を右端から数えて n 桁目の数字を P(n) とし、n が奇数なら1、偶数なら2を掛けて合計する。`9 −（合計 ÷ 9 の余り）` が検査数字。

## 8. 確認画面

`app/review.py`。Streamlitで1画面。

- 要確認の一覧（ファイル名、発行元、引っかかった理由）
- 1件を開くと、左に請求書の画像、右に読み取った値の入力欄
- 値を直して「検算する」を押すと、7をやり直して結果を出す
- 通ったら「承認」で本番テーブルへ移し、原本を `done/` へ移す
- 直した項目は `corrections` に記録する

見た目は、実装の前に方向を提示して確認を取ること（CLAUDE.md参照）。

## 9. 試験データ

`sample_data/` に架空の請求書30枚と正解データがある。書き換えないこと。

- `invoices/invoice_01` 〜 `invoice_30`（PDF 24枚、JPG 6枚）
- `ground_truth.csv`：1行が1枚。列名は日本語
- `ground_truth.json`：明細行つき

`ground_truth.json` のキーと、5のJSONとの対応：

| ground_truth.json | 5のJSON | 補足 |
|---|---|---|
| `file` | — | 拡張子なし。`scan` が真ならJPG、偽ならPDF |
| `invoice_no` | `invoice_no` | |
| `issuer` | `issuer` | |
| `regno` | `registration_no` | |
| `issue` / `due` | `issue_date` / `due_date` | |
| `x10` / `x8` | `taxable_10` / `taxable_8` | 税抜 |
| `t10` / `t8` | `tax_10` / `tax_8` | |
| `wh` | `withholding` | |
| `printed_total` | `total` | 紙に書かれている額 |
| `total` | — | 計算上の正しい額 |
| `err` | — | 空でなければ、検算で止まるべき |
| `layout` | — | A〜E |

様式：

| 様式 | 特徴 | 枚数 |
|---|---|---|
| A | 罫線の表、赤い角印が社名に重なる | 6 |
| B | 10%と8%が混在、値引き行あり | 6 |
| C | 和暦の日付、「金〇〇円也」の表記 | 6 |
| D | 内税（税込単価）、軽減税率は※印 | 6 |
| E | 個人事業主、源泉所得税の差し引きあり、支払期日に年の記載なし | 6 |

同じ発行元は同じ様式（1社3枚、全10社）。

わざと誤りを入れた3枚（検算で止まること）：
- `invoice_08`：記載の請求額が明細の合計と9,000円ずれている
- `invoice_15`：登録番号が1桁足りない
- `invoice_23`：支払期日が発行日より前

スキャン風の画像6枚：05、11、17、20、26、29

24枚のPDFには文字データが入っている。画像の読み取り精度を測るときは、PDFを画像に変換してから読ませる。

## 11. 測って記録する数字

- 項目ごとの一致率（請求額、登録番号、発行日、支払期日、請求書番号、発行元、税額）
- 誤りを入れた3枚を止められたか
- 正しい27枚のうち、誤って止めた枚数
- 文字抽出と画像読み取りの差
- スキャン風の6枚の精度
- 様式ごとの精度（A〜E）
- 1枚あたりの処理時間とAPIの費用
